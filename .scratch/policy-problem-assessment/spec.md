# 保单问题件判断系统：首版需求基线

Status: needs-info

更新时间：2026-09-10。本文汇总用户逐轮确认的需求，整体基线已获用户确认；待提供资料和待决策项集中列于末尾。用户要求按模块说明、实施和验证，目前仅模块一判断核心完成本轮验证，不代表具备真实业务上线条件。

## 1. 目标与范围

首版是独立系统，对投保申请进入外包审核前进行问题件识别，输出问题件、非问题件或无法判定及依据。选择规则较完整、有历史审核记录的产品试点；具体渠道与产品由业务指定。

本轮不触发业务分流，不替代正式核保审批，不包含理赔和批量判断。未来业务中，非问题件进入外包正常审核；问题件进入用户或机构修改、核实分支。

## 2. 使用流程与角色

逐单提交资料 → 后台执行检查并在页面显示进度 → 查看或导出报告 → 人工复核 → 补件后创建新判断。

首版新增独立的问题件判断入口，保留原问答入口，通过明确导航区分。问题件结论只由有完整检查记录的判断流程产生；聊天回答不作为正式判断报告。完整检查记录应如实包含未完成项目，不意味着所有检查均通过。

- 普通审核人员仅访问授权范围的数据。
- 业务管理员负责规则版本确认和人员授权，首版不开放自行注册。
- 优先复用公司身份认证；暂时无法接入时使用管理员分配的独立账号。
- 按团队或机构隔离访问。具体机构范围、账号和身份服务接入资料待提供。

## 3. 输入资料

- 保单整体信息采用 JSON，历史记录随资料提交；影像支持 PDF、JPG、PNG，保留原文件和页码。
- 独立试点通过人工导出脱敏数据模拟未来业务输入。未来业务可提供被保人、投保人的各类及累计有效保额；当前不视为已接入。
- 金额输入标明所属人员、保额类型、统计时点、是否包含本单以及完整性。
- 具体业务字段待脱敏样例到位后映射，不凭空定义保单结构。
- 每单附材料清单与完整性声明；其提供者及可信依据待明确。
- 生调、额外信息、通知单、体检通知等资料由适用规则决定是否必需，不要求每单提供所有材料。具体含义与触发条件待业务确认。
- 开发验证可使用合成或脱敏样本；合成样本不能证明实际业务判断准确率达标。

## 4. 规则来源、适用性与版本

复用 RAGFlow 已构建、上传和分片的数据集，不重建文档处理流程。现有知识内容包括各路渠道清单、银保通公共及产品核保规则、个险公共及产品核保规则、疾病查询手册。用户提供的手册名称为“简易荷包手册各类疾病查询”，正式名称待核对。

- 核保规则基本按规则编码与规则话术形成切片；疾病内容按疾病细类分类。
- 维护业务确认的适用必查项目清单。若暂无清单，整理与确认是试点前置工作。相关检索结果不能替代完整检查清单。
- 根据渠道、产品、适用版本确定规则集合，公共规则与产品规则共同检查。
- 只有业务明确规定覆盖关系时才覆盖；未明确的冲突记录为无法完成，不默认产品规则优先。
- AI 可辅助整理；未经确认的规则不参与正式判断。缺少执行条件时不能让模型猜测。
- 每次判断固定使用一套已确认规则版本，记录文档、切片及版本标识。必要时增加版本清单或隔离正式数据集；数据集 ID 本身不代表内容版本。
- 同编码的不同条件片段不能简单去重。若为同一规则分支，分别保存分支与来源。
- 疾病手册作为核查依据，不能把疾病或手册核保结论直接转换为问题件；需要业务确认的映射规则。

## 5. 检查与整单结论

单项检查结果：通过、发现问题、无法完成、不适用。

| 整单情况 | 结论 |
| --- | --- |
| 已有至少一个确定问题，包括同时存在未完成检查 | 问题件，保留未完成项目 |
| 未发现确定问题，但有未完成的适用必查项目或不能确认检查完整性 | 无法判定 |
| 适用必查项目全部完成且无问题 | 非问题件 |

- 非问题件不代表正式审核通过。
- 明确规则命中才形成确定问题；模型额外疑点单独展示，不冒充规则命中。
- 疑点涉及必查项目且无法核实时，对应项目无法完成；范围外提示不直接改变整单结论，报告注明检查范围。
- 已确认申请人未提交必交材料属于业务缺件；导入遗漏、识别失败不等同业务缺件。缺少可靠材料清单时只报告“本次未获取该材料”。
- 缺失项不阻止其他不依赖该资料的检查继续执行。
- 累计保额资料不完整时，对应项目无法完成，不能按部分金额判定通过。
- 年龄依业务确认的基准日计算；特殊人群按确认的代码映射。影像可以辅助提取，但模糊或冲突信息不由模型自行裁定。

## 6. 报告、复核与补件

报告支持页面查看及 PDF 导出，展示整单结论、检查范围、问题清单、未完成项目、证据位置、规则依据与版本、待补材料和建议处理动作。

- 说明哪里有问题、依据是什么、需补充或核实什么。
- 仅在权威材料明确支持时提出具体修改值；资料冲突时展示冲突，不自行选择。
- 支持人工复核记录，意见用于后续评测，不自动改变正式规则。
- 补件后基于完整资料快照重新检查全部适用项目，新建判断记录并保留旧报告。
- 展示资料变化、已解决／仍存在／新增问题及规则版本变化。
- 补件默认沿用原适用规则版本，除非业务明确要求切换；材料变化与规则变化分别说明。

## 7. 技术与数据边界

- 保留当前 Java 技术体系，复用 RAGFlow，通过配置接入公司批准的模型与影像识别服务。
- 缺少可用服务时，允许使用明确标识的模拟服务验证流程；模拟结果不能作为真实业务判断。
- 真实资料仅使用公司批准的处理服务；日志不记录完整保单和影像内容。
- 具体运行环境、服务能力、访问配置、资料保留期限及单次处理规模待确认。

## 8. 验收

### 已确认的工程硬门槛

- 未完成适用必查项不得输出非问题件。
- 确定问题具有可定位的依据，判断记录可追溯。
- 补件不覆盖历史；完整资料重检可呈现结果变化。
- 机构间不能越权访问。
- 异常和重试不破坏已有记录；模拟运行明确标识。
- 年龄与金额比较覆盖边界情况，包括恰好10周岁、恰好18周岁及金额等于／超过限额；具体预期基于已确认的业务口径。

### 已确认的业务验收原则

建立人工确认的固定评测集，保留一部分作为独立验收集。分别统计漏判率、误判率和无法判定率，明确各自分母，并按问题类型分析。

具体指标口径、样本量、各类错误代价与阈值由业务负责人确认，须在实际业务上线前确定。不能用合成数据结果宣称业务准确率达标。

### 已确认的交付安排

- 第一阶段：完成功能闭环，允许使用合成或脱敏数据，以及明确标识的模拟服务，验证逐单提交、后台检查及进度、报告与导出、人工复核、补件重检和权限隔离。
- 第二阶段：业务资料与批准服务齐备后，进行真实服务联调和业务质量验收。
- 两阶段分别验收功能和业务质量。业务数据未准备好时可以推进功能开发，但不宣称具备真实业务判断能力。
- 目标日期尚未指定。具体容量与耗时用户明确表示暂时未知，保留为待测，不作达标承诺。

## 9. 用户提供的规则样例

原文用于建模，尚不代表已确认全部执行口径或正式生效版本。

> 核保规则编码:YBCR0043; 核保规则话术:银保公共规则：特殊人群（农民、成年学生、无业人员、家庭主妇、离退休人员、司机）累计自驾车意外风险保额最高300万。

> 核保规则编码:YBCR0045; 核保规则话术:被保险人不满10周岁，人身险风险保额不得超过20万。

> 核保规则编码:YBCR0045; 核保规则话术:被保险人已满10周岁但未满18周岁，人身险风险保额不得超过50万。

待业务补充：

- 两段 YBCR0045 是否属于相同版本和适用范围下的条件分支。
- 各种风险保额的定义、币种、统计范围、保单状态、时点、是否含本单及重复数据处理；不得将 YBCR0043 的累计口径自动套用于 YBCR0045。
- 业务输出的有效保额与规则风险保额的字段映射。
- 年龄基准日及周岁口径、特殊人群代码映射。
- 条件缺失时保留无法完成，不编造正式判断。
